왜 커널 1.62배가 전체 1.28배인가?

같은 recycle4로 일반 compile과 CUDA graph 재생을 별도 측정했습니다. Graph는 CPU의 반복 준비·호출을 우회하는 진단이며 실행 중인 학습에 적용하지 않았습니다.

남은 호출부 문제: 우선순위

  1. B7의 반복 파일 작업 제거: Plan 생성 때마다 T.compile을 거쳐 source read/hash/cache-directory/lock/exists 확인. 재컴파일은 아니지만 backward20회마다 반복. Worker cProfile에서 Plan20회 약25ms, 그 안의 compile-cache 확인 약15ms. 이 수치는 계측 중 시간이며 그대로 절감된다는 뜻은 아닙니다.
  2. 고정 설정과 실행 계획 재사용: wide forward의 selection.json을32회 읽고 D128 backward의 configs.json도20회 읽습니다. 고정 cubin/launch 속성·구조체 레이아웃은 매 step 만들 필요가 없습니다.
  3. 호출 인자 포장 줄이기: Forward에서224회 인자 포장, tensor_map wrapper884회. 인코딩 캐시가 있어도 메타데이터 검증과 Python 객체 생성은 반복됩니다. 주소·stream을 갱신하는 재사용 가능한 실행 인자 구조가 필요합니다.
  4. 작업 버퍼 수명 관리: B1/B7은 매번 출력/partial/ring 버퍼를 요청합니다. 현재 torch.empty 호출이 매번 cudaMalloc을 뜻하는 것은 아닙니다. 재사용은 동시 forward와 stream 간 충돌 없이 구현해야 합니다.
